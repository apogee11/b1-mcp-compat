# An unresolved mapping behaves like the native Service Layer, and fails closed only for personal data

When neither the knowledge base nor the company's user catalog explains a property, the connector does not invent a label or a column (no naming convention: `Phone1` is `Tel1`). For metadata it does what the native Service Layer does for the same case (serve the property without the annotation it cannot know); an entity set is not turned into an error when a transparent answer exists. The exception is the personal-data action: an unresolved mapping there fails closed, because a silent miss could hide a personal field.

> Status: implemented (B1 closed, 2026-10-21, rea/01-findings.md sections B1 to B1d). Rules verified: a user field (`U_`) the catalog does not list for a standard table is left out of the answer; a property named like its type is exposed as `<Type>Property` and resolved by its engine name; an enum member with no stored value is served without `ValidValue`; an entity set without a table is served with an empty table name. A standard property or entity set that the knowledge base does not know can only happen with a Service Layer build different from the one the knowledge base was extracted from (the native engine knows it from its own dictionary, which the connector lacks). That case keeps failing with HTTP 502 naming the property and pointing to `compat/CHECK-YOUR-BUILD.md`, and is not guessed. The personal-data action fails closed.
